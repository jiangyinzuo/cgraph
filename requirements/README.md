# cgraph 需求管理

本目录是用户可观察产品行为的唯一规范来源。根目录 `DESIGN.md` 只保留产品愿景、范围和需求导航；`docs/` 解释已经交付的用户用法；`src/` 记录实现原理与技术决策。

## 父子结构

- 顶层目录代表父需求，目录名使用 `REQ-N-slug`，数字不加前导零。
- 父需求的 `README.md` 描述共同目标、范围、整体验收条件和子需求清单。
- 子需求使用 `REQ-N-M-slug.md`，只拆分能够独立实现、验收或延期的行为。
- 父需求可以没有子需求。此时父文件本身就是最小可交付需求，并直接记录验收条件。
- 子需求暂不继续嵌套；出现第三层需求时，应先验证父需求是否过大，再修改本规范。

## 状态

| 状态 | 含义 |
| --- | --- |
| `Draft` | 仍在澄清，不能据此承诺实现 |
| `Planned` | 行为和边界已接受，但尚未开始 |
| `In Progress` | 正在实现，尚未满足全部验收条件 |
| `Partial` | 部分行为已可使用，但需求整体未完成 |
| `Implemented` | 代码、验收、用户文档和内部设计均已完成 |
| `Deferred` | 已接受但当前里程碑明确不实现 |
| `Rejected` | 已决定不实现，并应记录原因或替代方案 |

父需求有子需求时，状态按以下规则维护：全部适用子需求完成才是 `Implemented`；已有部分交付时是 `Partial`；没有任何实现时是 `Planned`；`Deferred` 子需求不会被默认为已完成，父文件必须说明它是否阻塞父需求完成。

## 优先级

| 优先级 | 含义 |
| --- | --- |
| `P0` | 当前可用主流程不可缺少 |
| `P1` | 下一个完整产品里程碑需要 |
| `P2` | 明确需要，但不阻塞近期主流程 |
| `P3` | 探索性或长期增强 |

优先级不是实现状态，也不代表承诺日期。目标版本尚未建立时使用 `TBD`，不要猜测发布日期。

## 需求文件模板

```markdown
# REQ-N-M：需求名称

| 字段 | 值 |
| --- | --- |
| 父需求 | `REQ-N` |
| 状态 | `Planned` |
| 优先级 | `P1` |
| 目标版本 | `TBD` |

## 目标

## 需求

## 验收条件

## 当前实现与差距

## 关联文档
```

## 维护规则

1. 产品行为改变时，先修改对应需求及验收条件，再同步用户文档和内部设计。
2. 新需求先判断属于现有父需求还是需要新的父需求；不要把功能列表重新堆回 `DESIGN.md`。
3. 标记 `Implemented` 时必须列出实现或测试证据，并确认 `docs/` 没有相反描述。
4. 技术方案变化但用户行为不变时，只修改 `src/` 设计或 decision 文档，不制造新的产品需求。
5. TODO 应尽可能引用需求 ID；没有对应产品行为的纯重构 TODO 留在内部设计中。
6. 本索引中的状态必须与各父需求文件一致；父子状态变更应在同一次修改中完成。
